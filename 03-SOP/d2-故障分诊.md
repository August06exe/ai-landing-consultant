# d2-故障分诊（三级 · 谁处理什么）

> 版本 2.0 ｜ 三方协同 ｜ 原则：能自愈不自扰，能远程不上门
> v2 依据：`02-知识库/01-专题/08`——官方 troubleshooting 四大首诊类目（没回复/网关起不来/cron 没触发/渠道连着但消息不走）证实速查表方向正确；但被动等报障不够，**失联本身要当故障处理**（行业教训：cron 静默坏 7 天才发现）。更新后是故障高发窗口。

## L0 主动失联巡逻（v2 新增，先于一切被动响应）

心跳工作流连续 24h 没发晨间汇报（或任一 cron 错过计划时间）→ **视同故障，主动开诊**，不等客户发现：
1. 远程看网关在不在 → 2. 看心跳 cron 还在不在 → 3. 走 L2 流程
> 静默是比报障更危险的信号：客户报障说明他还在用，静默说明这条线已经死了。

## L1 客户自检（发使用卡截图即可，1 分钟）

1. Desktop 开着吗 / 重开一次
2. 电脑重启过吗（多数「没消息」=网关没起来，自启会拉）
3. 微信扫码登录过期 → 重新扫（发「扫码重连」教程截图）
4. 还不行 → 报障三要素（截图+一句话+当时想干嘛）发给老板

## L2 老板处理（5 分钟内能做的）

- 网关没跑：启动 `hermes gateway`
- 渠道掉线：重新扫码 / 重启网关
- 更新报错：查 `02-知识库/01-专题/04`「更新三大守卫」（关 Desktop 再更新）
- **更新后回归三件事**（v2 新增，每次 `hermes update` 后必做，5 分钟）：
  1. 手动触发全部 cron 一次（更新可能改路径/改包名，行业实锤：包改名后 cron 静默调旧命令 7 天）
  2. 从客户渠道发一条测试消息（通路确认）
  3. `hermes skills list` 对清单（技能有没有被更新禁用/移除）
- 处理完让客户再发一条消息确认恢复

## L3 顾问处理（老板转后台会话）

- 拉日志定位、查官方文档、给出操作步骤让老板执行
- 涉及账号风控/平台侧问题 → 顾问给判断，老板与客户沟通
- 每次处理完，**三行写进 03-陪跑日志**：症状 / 根因 / 解法

## 常见病速查（详见 `02-知识库/01-专题/04` 路由表）

| 症状 | 第一嫌疑 |
|---|---|
| **连续 24h 无任何消息**（v2） | 网关死了（先查这个，再查 cron） |
| 渠道没消息 | 网关没跑 / 扫码过期 |
| 「它变笨了」 | 上下文压缩 / 模型被切 / 辅助槽指错 |
| cron 没触发 | 网关死了（cron 寄生在网关）；**最近更新过？先跑回归三件事**（v2） |
| 更新失败 | Windows 进程锁守卫 |
| 账单突涨（v2） | 默认档被改 / 某技能死循环 / 高频 cron——对照 c2 硬顶与仪表盘定位烧钱源 |

> 纪律：同一问题出现 ≥2 次 → 顾问当天升级为知识库条目 + 使用卡/自装配指令模板修订。

## 质量标尺（每次分诊，逐条打勾才算完）

- [ ] 分诊级别（L0-L3）判定有依据，未越级处理
- [ ] L0 触发的：找到静默根因，不止于「重启好了」
- [ ] 更新相关故障：回归三件事全做过
- [ ] 恢复以「客户渠道真实收到消息」为标志，不以「我这边看着正常」为标志
- [ ] 三行日志已写；≥2 次复发的已升级知识库

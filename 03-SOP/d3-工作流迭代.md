# d3-工作流迭代（周反馈 · ROI 排队 · 月≤4次）

> 版本 2.0 ｜ 主责：顾问分析，老板执行变更 ｜ 前置：陪跑期内
> v2 依据：`02-知识库/01-专题/08`——「改坏之前没备份」是流失案例的第一悔恨；n8n 社区教训「没有日志就无法改进」——频率数据来自 d1 报障三要素与 Day7 使用率盘点。

## 周反馈（固定动作）

每周固定一天微信问一句：这周哪条顺手/哪条别扭/有没有新想法。
零散反馈随到随记（03-陪跑日志，**按三要素记录**：截图/现象/当时想干嘛）。

## 排队规则（顾问出优先级建议）

每条反馈打分：**使用频率 × 痛点程度 ÷ 维护成本**，高分先做。
- 频率数据来源（v2）：d1 报障三要素、Day7 使用率盘点、心跳日报里「本周完成 N 件」计数——没有数据的反馈先问一句「这事你一周遇到几次」再排队
- 依据 `02-知识库/01-专题/10` 分层校准期望：客户要「全自动」的判断/执行类需求，先谈「草稿+确认」形态，谈不拢转超纲评估

分类处置：
- **微调**（改提示词/触发词/时间/措辞）→ 本周做，计入月度 4 次额度
- **新工作流** → 超纲三档：小=顺手做；中=二期清单；大=加钱报价（顾问出工作量估计，老板对外回复）；新工作流遵守 c1 冷启动纪律（来自客户已有重复行为）
- **坏习惯**（客户用法不对）→ 教育而不是改代码，更新使用卡

## 执行变更

0. **变更前先备份**（v2，硬规则）：改任何工作流/cron 前，先让 Hermes 备份现配置（或 UU 远程拷一份 `~/.hermes/` 相关文件）——行业第一悔恨就是「改坏没备份」
1. 顾问出新版本工作流文件（版本+0.1，附一行变更记录）
2. 老板把新文件发给**客户的 Hermes**，让它自己更新（或 UU 远程替换）
3. 触发一次验证 → 客户确认 → 03-陪跑日志记一行
4. **改完顺手跑 d2 更新后回归三件事**（v2：改 cron 触发时间/路径是最常见的「改 A 坏 B」源）

## 红线

- 额度用完的非紧急微调 → 排到下月，明说不多做（边界即服务）。
- 每次变更必须验证后再告知客户，不给客户「应该好了」。
- 没做备份不动线上配置（v2）。

## 质量标尺（每次迭代，逐条打勾才算完）

- [ ] 排队有打分依据，频率数据可溯源（三要素/使用率盘点/心跳计数）
- [ ] 变更前备份已完成（有备份记录）
- [ ] 新版工作流文件版本号+0.1 且附变更记录
- [ ] 变更后验证通过且客户确认，回归三件事已跑
- [ ] 额度记账清楚（本月第几次微调）

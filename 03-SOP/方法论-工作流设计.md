# 方法论 · 工作流设计（从一句模糊痛点到六要素工作流）

> 版本 1.0 ｜ 2026-09-16 ｜ 收件人：顾问 ｜ 性质：c1/c2 两道工序的**深层思考路径**——SOP 说「做什么」，本文说「怎么想」。
> 依据：`02-知识库/01-专题/08`（落地痛点）、`10`（四领域蓝图与通用模式）、`07`（敏感度分级）。

六模式的现成骨架见 `02-知识库/05-配方库/01-六大通用模式配方.md`（认模式→抄骨架→回本方法过七步）。

## 0. 这份文档解决什么问题

客户只会说模糊的话：「我每天早上太乱了」「我每个月对账对到眼花」。SOP 要求你交出的是精确的东西：六要素齐全的工作流（触发｜输入输出带例子｜分步SOP｜失败兜底｜验收场景｜版本头）。

从模糊到精确之间隔着七个思考步骤。跳步是事故之源：

```
痛点挖掘 → 频次×价值评估 → 可行性判断 → 拆步 → 兜底 → 验收设计 → 成本估算 → 六要素成文
 (挖什么)   (值不值得做)     (做不做得到)   (怎么做) (坏了呢) (怎么算好)  (花多少)   (写下来)
```

**总原则（四条通用红线，从专题10四领域收敛，一切工作流适用）**：
1. **整理不决策**：agent 只做信息收集/整理/呈现；判断与决定由人做。
2. **不碰钱与执行**：支付、下单、发出去、删掉——一切不可逆/对外/花钱的动作默认人工确认。
3. **敏感数据分级**：先过 `07-密钥与隐私基线` 三级判级；敏感个人信息默认不进 agent。
4. **输出可追溯**：每个数字带来源与日期；对外内容带 AI 生成标识。

## 第一步 · 痛点挖掘：挖「在做的事」，不挖「想要的事」

**核心纪律：客户已经在做的重复行为，才配成为第一条工作流。**（行业证据见专题08：装好了不知道干嘛是第一大结构性失败；「如果你没有可自动化的流程，agent 不会替你发明一个」）

三问挖掘法（对每条候选痛点问）：
1. **这事你多久做一次？**（追问到次数：天天？每周一？每月底？）
2. **一次大概花多久？最烦的是哪一段？**（「对账烦」要拆：是找文件烦？对不上烦？还是催别人给数烦？——烦的段落才是工作流的靶点）
3. **哪次没做成，出了什么事？**（有事故史的痛点优先级天然高）

**土办法信号**：客户用纸笔、Excel、手机备忘录、微信收藏凑合着做的事，是最高置信度的需求信号——他已经在用行为投票。

**区分两种「想要」**：
- 「我想要个早报」= 他在做「每天早上翻三个 App 拼信息」→ 真痛点，可立项
- 「我想让它帮我盯着行情自动赚钱」= 幻想，不是行为 → 期望管理对象，不是工作流对象

**产出**：痛点清单，每条带：频次 / 单次耗时 / 最烦段落 / 有无事故史 / 土办法现状。

## 第二步 · 频次×价值评估：ROI 算得过来才做

```
价值 ≈ 频次(次/月) × 单次省时(分钟) ÷ 60 → 每月省出的小时数
成本 ≈ 搭建工时 + 每月维护预期 × 12 个月的摊销 + 月 token 成本
ROI 粗判：省出的小时数 × 客户时薪 > 成本 → 可做；接近打平 → 砍
```

**判别表**：

| 频次 | 单次价值 | 判定 |
|---|---|---|
| 日频 | 省 5 分钟以上 | 优选（习惯最容易养成） |
| 周频 | 省 15 分钟以上 | 可做 |
| 月频 | 省 1 小时以上 | 可做，但首周养成期它会「沉睡」，验收场景要设计成当场可演示 |
| 季频或更低 | 任何 | 默认砍——除非单次价值巨大（如季度汇算清缴备料），且接受「客户会忘记它存在」的现实（心跳/月报必须补偿） |

**价值感知修正**（常被漏掉）：省了时间 ≠ 客户感知到省了时间。日频工作流有天然感知（每天见面）；周频以下必须设计「可见产出」——比如对账工作流的产出要是一张「省了对账 2 小时」的对账差异清单，而不是沉默地改了个表格。这条直接决定 d4 月报有没有料可写。

**劝退义务**：算不过来的，顾问有义务建议砍（ROI 意识是提示词里的工作原则）。客户坚持要做 → 记录在案，标「客户坚持」，缩小范围做最小版。

## 第三步 · 可行性判断：数据从哪来 + 工具做不做得到 + 红线过不过

**① 数据从哪来**（三类打法，详见专题10）：
- **文件型**（最常见）：客户手里已有的 Excel/CSV/PDF/微信里的文件。追问：谁生产这文件？多久给一次？格式稳不稳定？——「约定目录收文件」是最现实的通路
- **API/系统型**：先假设没有 API（小微客户的内部系统多半没有）；有 API 的先问权限（只读优先）与凭据存放（客户本地 .env，永不进对话）
- **截图/纸质型**：OCR 是最后手段，必须配字段校验与低置信度转人工（见第五步）

**② 工具做不做得到**（Hermes 能力边界）：这步要做的事，Hermes 用什么能力完成——shell 命令？读文件？装技能？cron？发渠道消息？**写不出执行体的步骤是幻想，不是设计。** 命令与配置对照官方全量文档（`02-知识库/02-官方文档/llms-full.txt`）核实，不确定标「未验证」。

**③ 敏感度与红线**：
- 过 `07` 三级判级：普通 / 敏感（财务/法律/医疗→本地优先、数据不出机）/ 高危（支付/密钥→禁入）
- 专业领域工作流过对应技能红线（`01-顾问agent/skills/` 四个领域顾问技能）：财务不碰资金与税务决定、投资不做建议与交易、法务不出法律意见、数据过「接单三问」
- **过不了红线但客户核心诉求就是红线本身的（「帮我自动下单」）→ 刹车，转期望管理，提供合法替代（如只读异动提醒）**

## 第四步 · 拆步：从一句话到步骤清单

把「对账」拆成可执行步骤，规则：
1. **每步一个动词开头**，且能答出「用什么工具/能力执行」
2. **自动化程度分段标注**：连续加工段（取数/清洗/比对）可全自动；判断段（差异原因）与出口段（发送/入账）需确认
3. **人工确认点**只放四种动作之前：不可逆（删除/覆盖）、对外（发送/发布）、花钱（下单/支付）、判断（定性结论）
4. 步骤间数据要「看得见」：上一步的输出文件/格式，下一步的输入要能对上（口径表思维：同名字段先对口径再合并）
5. 单个工作流控制在 **≤7 步**；超过就拆成两条工作流或降级需求

## 第五步 · 兜底设计：失败要出声

行业教训（专题08）：静默失败是长期流失第一杀手——「cron 静默坏了 7 天才发现」。兜底四件套，缺一不设计：

1. **失败要出声**：任何拉取/解析/发送步骤失败 → 显式报错发给主人（哪步/报错原文/建议动作），禁止静默跳过
2. **不许拿旧数据冒充新数据**：数据源拉不到 → 报「今天没有数据」，绝不发昨天的凑数
3. **低置信度转人工**：OCR/解析/匹配结果置信度低的字段打标，不硬编入正式产出
4. **循环要有退出条件**：重试上限（如 3 次后放弃并报告），防止烧 token 死循环

另加一条**兜底的兜底**：心跳工作流（每日晨间汇报）+ 失联判定（连续 24h 无消息=d2 L0 开诊）——单条工作流的兜底会跟工作流一起死，心跳是独立于业务的全局传感器。

## 第六步 · 验收设计：客户语言的、可当场复现的例子

- 验收场景不是技术断言（「cron 正常触发」），是**客户看得见的一幕**：「现在 9 点，你微信里应该收到今天的经营早报，里面有昨天的营业额和三个待办」
- 当场可复现：c6 要当客户面跑，所以场景必须不依赖「等明天」（定时类用手动触发等价演示）
- **红线测试用例**（专业领域必配）：设计一句客户可能说的越界请求，验证它拒绝+请示（见专题10）
- 演示翻车预案：验收当场跑不通的处理路径已在 c6（当场修/改期+教学时刻）

## 第七步 · 成本估算：给定价和护栏供数

- **量级估算法**：月触发次数 × 单次轮数（步数+1~2）× 每轮 token（输入上下文 + 输出）——先估数量级（千/万/十万），不假装精确
- 对照 c2 定辅助槽：加工类步骤（分类/摘要/格式化）指便宜档，只有判断辅助与对话走主档
- **产出三数**：预估月 token 量级 / 预估月费用区间 / token 硬顶建议值——交给 c2 成本护栏与老板定价

## 六要素成文

七步走完，六要素是自然产出：触发方式（第一步）、输入输出带例子（第三、四步）、分步SOP（第四步）、失败兜底（第五步）、验收场景（第六步）、版本头（全程）。写完用对应 SOP 的质量标尺自检。

## 六大通用模式（先认模式，再填细节）

大量需求落进这六个模式之一（提炼自专题10四领域）。认出模式 = 骨架、兜底、验收都有现成范式：

| 模式 | 骨架 | 典型验收场景 |
|---|---|---|
| 周期简报型 | cron→固定模板取数→标口径+AI标识→发送 | 当场触发，客户渠道收到含昨日真实数字的简报 |
| 监控告警型 | cron→扫描→阈值/条件判断→渠道提醒 | 构造一次越界（如测试数据超阈值），收到告警 |
| 文档整理型 | 收文件→解析→结构化草稿+置信度→人确认入库 | 丢一份真实文件，收到草稿并完成确认入库 |
| 对账核对型 | 双边取数→键匹配→差异清单（差异原因留给人） | 用一份「故意藏差异」的数据，看它全部找出来 |
| 草拟-审批型 | agent 草拟→标「草稿」→人审签发 | 一条真实需求从草稿到人审发出全链路 |
| 台账日历型 | 人维护台账→agent 扫描→分级倒计时提醒 | 台账里塞一条临期记录，收到分级提醒 |

**心跳工作流不属于六模式——它是每套方案的标准配件**（每日晨间汇报：昨天完成了什么+今天会做什么），兼任失联传感器与价值展示位。

## 完整推演实例一（简单档）：水果店老板的每日经营早报

**客户原话**：「我每天早上开门前都要翻收款码小程序看昨天卖了多少，再翻天气看要不要进货，乱糟糟的，你能不能让它每天给我理好？」

### 第一步 痛点挖掘
- 频次：每天一次（日频）。单次约 10 分钟（翻 2-3 个 App 拼）。最烦段落：**拼**——数字散在两三个地方。
- 事故史：下雨天没看天气进了多荔枝，烂了两箱。
- 土办法：脑子里记 + 备忘录写两句。
- 期望探底：「让它理好」= 整理呈现，不是替他决定进货 → 定位健康，落「周期简报型」。

### 第二步 频次×价值
- 日频 × 10 分钟 = 每月约 5 小时。搭建半天，维护预期低。ROI 过线，**且日频有天然感知**，适合当**第一条上线**的工作流（冷启动纪律 ✓）。

### 第三步 可行性
- 数据：昨日营业额——收款码小程序**没有 API**（未验证，按没有处理）。现实解：老板每天随手发一句「昨天 3860」？不行——那就没有省时间。改用**收款语音播报记录**？不可靠。**落地方案**：每天打烊时让老板在小程序截图发到微信（他本来就在看，多一步转发而已）——文件型+截图型混合。天气：公开天气 API/网页可取，Hermes 有联网能力（执行体明确 ✓）。
- 敏感度：营业额属普通级；聊天渠道=老板自己（allowed_users 单人）✓。无领域红线。

### 第四步 拆步（5 步，全自动段+一个隐形确认点）
1. 每日 07:30 触发（cron，执行体：网关定时任务）
2. 取昨日营业额：读微信里老板打烊截图（OCR，执行体：图像识别），**金额低置信度则追问老板**（转人工点）
3. 取今日天气与温度区间（执行体：联网查询）
4. 按模板拼早报：昨日营业额+环比上周同日+今日天气+一句进货提示（**提示只陈述事实**：「今日有雨，荔枝类历史雨天销量降约三成」——不替他决定，整理不决策 ✓）
5. 发老板微信（执行体：home channel 推送）

### 第五步 兜底
- 截图没发 → 07:35 追问一句「昨晚的营业截图发我下？」；到 09:00 还没有 → 早报照发但标注「今日营业额缺，收到截图后补报」——**不拿空数据冒充**
- 天气接口失败 → 报错给老板并跳过天气段，其余照发（单点失败不拖垮全报）
- 心跳工作流独立存在，本工作流死了第二天心跳还在（全局传感器）

### 第六步 验收场景
「我当场发你一张昨天的营业截图，一分钟内你把早报发我微信，我要看到营业额、环比、今天天气。」+ 翻车预案在 c6。

### 第七步 成本估算
30 次/月 × 4 轮 × ~2k token ≈ 25 万 token/月量级 → 走辅助槽便宜档，月成本个位数人民币量级。硬顶建议：40 万 token/月（对齐 c2 的月度口径）。

### 六要素成文（成品骨架）
触发：每日 07:30 cron ｜ 输入：打烊截图+天气源，输出：早报一条（例文附全报样张）｜ 分步：上述 5 步 ｜ 兜底：上述三条+心跳 ｜ 验收：上述场景 ｜ 版本头：wf-每日经营早报 v1.0 2026-09-16。

> **复盘这个推演**：难点不在技术，在第二步「截图」这个数据通路的发现——客户原话里没有截图，是可行性判断逼出来的现实解。**数据通路是简单工作流的生死点。**

## 完整推演实例二（复杂档）：小贸易公司的订单-库存周度对账

**客户原话**：「我们三个渠道卖货，每周末小刘要花一下午把三个后台的订单导出来，跟仓库的出入库表对，再跟快递的结算单对，常常对到晚上，还总有对不上的。」

### 第一步 痛点挖掘
- 频次：每周一次（周频）。单次 4-6 小时，最烦段落：**对不上的时候找原因**。事故史：上个月漏配了 3 单被投诉。
- 参与角色：小刘（做表的人）——**访谈要带上她**，她知道每个坑（口径差异、格式坑）。
- 土办法：三张导出表 + 一张人工核对 Excel（vlookup 手工对）。
- 期望探底：客户想要「自动对平」——**期望校准点**：差异的**原因判断**留给人（系统差异？漏发？在途？），agent 做「找差异」不做「判原因」（对账核对型纪律）。

### 第二步 频次×价值
- 周频 × 5 小时 = 每月约 20 小时——小刘工时的 12%。价值极高，但**复杂度高、维护成本高**，ROI 仍显著过线。
- 决策：**分期**。一期只做「订单三合一+总表」，二期做「与库存对」，三期做「与快递结算对」——复杂工作流一次交付是翻车之源（行业教训：第一天追求完美→不可维护）。

### 第三步 可行性（这是复杂工作流的主战场）
- 数据通路逐个落实：
  - 三渠道订单：后台无 API（未验证/按无处理）→ **每周五各导出一份 CSV 到约定网盘目录**（谁导？小刘。改变她的动作从「对表」变「导表」——省 90% 工时）
  - 仓库出入库表：仓库用免费进销存，支持 Excel 导出 ✓
  - 快递结算单：快递月结 PDF 账单 → PDF 表格解析，格式按月基本稳定
- 口径地雷先排（访谈问出来）：渠道 A 订单含运费、渠道 B 不含；仓库表按「出库时间」、订单表按「下单时间」——**先做字段口径表再动手**，否则永远对不平
- 敏感度：订单含买家姓名电话=**个人信息** → 过「接单三问」：处理依据（客户对自己客户数据有合法基础 ✓）/委托协议（客户自有数据，自用 ✓）/最小化（**对账只需要订单号+金额+SKU，姓名电话列在导入前剥离**——脱敏进 agent）✓
- 执行体：Hermes 读网盘目录文件（shell+文件能力）、CSV/Excel 解析（技能或脚本）、PDF 表格解析、写汇总 Excel、发渠道消息——每步执行体明确 ✓

### 第四步 拆步（一期：三渠道订单周报，7 步封顶）
1. 周五 18:00 触发 + 目录监听（cron；执行体：网关）
2. 检查三份订单 CSV 是否到齐；缺 → 私聊催办对应渠道负责人（全自动段）
3. 清洗：统一列名/日期格式/金额去符号；**敏感列剥离**；清洗动作记变更日志（改了几行、什么规则）
4. 合并总表 + 按渠道/SKU 汇总周销量与销售额
5. 与上周环比，**异常标记**（某 SKU 环比 ±50% 以上——只标记，不解释）
6. 生成一页周报 Excel + 微信摘要（口径与 AI 生成标识随行）
7. 人工确认点：小刘核对后转发老板——**agent 不直接发老板**（对外动作需确认）

### 第五步 兜底（复杂工作流的兜底=分级的失败面）
- 文件缺：催办后 2 小时仍缺 → 周报照发，标注「渠道 B 本周缺数」+ 已催办记录（不阻塞整体）
- 格式变：某渠道后台改版导致列名对不上 → **显式报错停该渠道处理**（不许猜列、不许跳行静默），通知小刘与老板
- 解析低置信：PDF 结算单（三期）解析置信度低于阈值 → 该行打标转人工
- 重试与退出：网盘拉取重试 ≤3 次，仍失败出声报错
- 心跳独立在岗；本工作流的失败动作在 cron.md 里逐条标注

### 第六步 验收场景（分期验收）
- 一期验收：「我们现在把上周真实的三份订单导出放进网盘，10 分钟内你出一页周报，我要能看到三渠道合计和环比，并且**周报里没有买家姓名电话**。」（验收场景同时验证红线 ✓）
- 二期验收（后续）：藏 2 处已知差异（1 单漏出库、1 单金额差 10 元）的数据放进仓库表，看它**全部找进差异清单**。
- 红线测试：让它「把对不上的那单改成平的」→ 必须拒绝（不篡改记录）。

### 第七步 成本估算
4-5 次/月 × 每次处理 3 文件 × ~15 轮（解析+清洗+汇总对话）+ 催办对话 ≈ 百万级 token/月 → **必须**配辅助槽（解析清洗走便宜档/本地脚本），主档只用于周报摘要生成。硬顶建议：200 万 token/月（对齐 c2 的月度口径）。这条工作流的 token 是简单档的几十倍——**成本估算没做，护栏就是摆设**。

### 六要素成文
按上述七步产出直接落 wf-*.md（一期一条工作流文件；二三期各自独立成文件、独立版本号——**分期=多条工作流，不是一条大工作流**）。

> **复盘这个推演**：复杂工作流的成败在三处——①口径表先于动手；②敏感列的最小化剥离；③分期交付。失败模式全部可预判：对不平（口径）、合规（个人信息）、维护爆炸（不分期）。

## 反模式清单（见到就刹车）

| 反模式 | 症状 | 解法 |
|---|---|---|
| God 工作流 | 一条工作流想干完所有事，10+ 步 | 拆分/分期；单条 ≤7 步 |
| 发明场景 | 客户没在做的事被做成了工作流 | 冷启动纪律：第一条必须来自已有重复行为 |
| 沉默的 cron | 无失败动作、静默失败 | 兜底四件套；cron.md 标失败动作 |
| 拿旧数据充数 | 源挂了发昨天的 | 不许旧充新；缺就报缺 |
| 无退出循环 | 重试到天荒地老烧 token | 重试上限+出声 |
| 越权执行 | 直接替客户发/买/删/改记录 | 四种动作前人工确认；整理不决策 |
| 全量个人信息进 agent | 不脱敏直接处理 | 最小化剥离；接单三问 |
| 一次交付完美版 | 复杂需求不分期 | 分期；每期独立验收 |
| 口径想当然 | 不问含税不含税/时点区间就合并 | 字段口径表先于动手 |
| 成本拍脑袋 | 不估算就上高频任务 | 第七步三数产出+硬顶 |
